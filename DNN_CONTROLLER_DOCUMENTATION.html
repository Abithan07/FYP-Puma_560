1. System Overview & High-Level Architecture

The DNN-based controller for the PUMA-560 arm is a hybrid control architecture that combines deep neural network (DNN) feedforward torque prediction with classical PID feedback control. This synergistic approach leverages the strengths of both paradigms:

DNN Feedforward

  • Learns inverse dynamics from data
  • Predicts required torques for desired trajectory
  • Handles complex nonlinear dynamics
  • Fast online inference (~1-2 ms per step)

PID Feedback

  • Corrects tracking errors in real-time
  • Compensates for model imperfections
  • Adapts to disturbances & uncertainties
  • Ensures closed-loop stability

The controller executes in two phases:

  1. Phase 1 (Stabilization): PID-only controller moves arm to trajectory start pose
  2. Phase 2 (Trajectory Tracking): DNN + PID executes desired trajectory at 100 Hz

3. DNN Inference Pipeline (DeLaN + GRU)

The DNN component has a two-stage architecture where each stage serves a distinct purpose:

3.1 Stage Overview

Stage Name Framework Purpose Active
1 DeLaN (Lagrangian Network) JAX + Haiku Physics-based baseline prediction of inverse dynamics Every step
2 GRU Residual PyTorch Learn temporal model errors as residuals After step 128

3.2 Two-Stage Prediction Formula

τ_dnn = τ_delan + τ_residual

where:
τ_delan = f_DeLaN(q, q̇, q̈) [always available]
τ_residual = f_GRU(history_buffer) [available after warmup]

Key Design Principle: DeLaN provides a physically-grounded baseline that captures the fundamental inverse dynamics (inertia, gravity, Coriolis). The GRU learns residual error corrections that account for unmodeled effects (friction, backlash, motor dynamics, etc.).

4. DeLaN: Physics-Based Baseline

4.1 What DeLaN Does

DeLaN (Differentiable Lagrangian Network) encodes robot dynamics using a learned Lagrangian formulation. Instead of learning torques directly, it learns the robot's mass matrix D(q), Coriolis forces C(q,q̇), and gravity vector G(q).

4.2 Mathematical Formulation

The robot equation of motion (Euler-Lagrange):

τ = D(q)·q̈ + C(q,q̇)·q̇ + G(q)

where:
τ = joint torques (3,) [Nm]
D(q) = mass (inertia) matrix (3,3) [kg·m²]
q̈ = joint accelerations (3,) [rad/s²] (desired)
C(q,q̇) = Coriolis/centrifugal matrix (3,3)
q̇ = joint velocities (3,) [rad/s]
G(q) = gravity vector (3,) [Nm]
q = joint positions (3,) [rad]

4.3 How DeLaN Learns These Terms

DeLaN uses neural networks to approximate each dynamic term:

  1. Mass Matrix D(q):
    • MLP network takes trigonometric features of q as input: cos(q), sin(q)
    • Outputs lower-triangular matrix L such that D(q) = L·L^T (positive definite)
    • Ensures physical consistency (symmetric, positive definite)
  2. Gravity G(q):
    • Separate MLP network learns gravitational torques
    • Also takes trig features of q as input
    • Outputs (3,) gravity vector
  3. Coriolis C(q,q̇):
    • Derived analytically using Lagrangian mechanics
    • Computed from Hessian (derivatives) of learned kinetic & potential energies
    • No separate network needed

4.4 Online Inference (100 Hz)

At each control step, DeLaN performs forward inference:

At timestep idx: q = [dp1[idx], dp2[idx], dp3[idx]] # desired position qd = [dv1[idx], dv2[idx], dv3[idx]] # desired velocity qdd = [da1[idx], da2[idx], da3[idx]] # desired acceleration 1. Forward pass through DeLaN network (JAX): D_matrix = network_D(cos(q), sin(q)) # (3,3) G_vector = network_G(cos(q), sin(q)) # (3,) C_matrix = compute_coriolis(lagrangian_derivs) # (3,3) 2. Compute inverse dynamics: τ_delan = D_matrix @ qdd + C_matrix @ qd + G_vector Result: (3,) torque vector Latency: 1-2 ms (steady state, after JAX JIT warmup)

4.5 Strengths of DeLaN

  • Physics-informed: Respects the structure of robot dynamics (mass, gravity, Coriolis)
  • Interpretable: Can extract learned D(q), G(q) matrices for analysis
  • Generalizable: Works well even outside training data because it encodes physics
  • Fast: Minimal latency (~1 ms) due to small network size
  • Always available: Active from step 1, no warmup delay

4.6 Limitations of DeLaN Alone

  • Model errors: Cannot capture unmodeled dynamics (friction, backlash, motor dynamics)
  • Training data dependency: Accuracy depends on quality of training dataset
  • Systematic bias: May systematically under/overpredict torques in certain configurations

This is where GRU residual learning comes in.

5. GRU Residual: Learning Model Errors

5.1 What the GRU Does

GRU (Gated Recurrent Unit) Residual is a recurrent neural network that learns the error between DeLaN's prediction and ground truth. It outputs a residual torque correction that is added to DeLaN's output.

5.2 Residual Learning Concept

τ_residual = f_GRU(history_buffer)

where history_buffer contains the last 128 timesteps of state & torque data

τ_actual_true ≈ τ_delan + τ_residual

GRU learns: τ_residual = τ_actual_true - τ_delan

Why this works: By learning only the difference, the GRU focuses on correcting DeLaN's errors rather than learning the full physics from scratch. This is more data-efficient and captures unmodeled effects.

5.3 GRU Network Architecture

Layer Type Input Size Output Size Purpose
1 GRU Cell 12 (features) 64 (hidden) Process timestep t
2 GRU Cell 64 64 Process timestep t+1
3 GRU Cell 64 64 Process timestep t+2
4 GRU Cell 64 64 Process timestep t+N-1
5 Linear (FC) 64 3 (torques) Output residual prediction

5.4 Input Features (12-Dimensional)

At each timestep, the GRU input is a normalized 12-D feature vector:

Input feature vector (12,): [q[0], q[1], q[2], # 3: Joint positions qd[0], qd[1], qd[2], # 3: Joint velocities qdd[0], qdd[1], qdd[2], # 3: Joint accelerations tau_delan[0], tau_delan[1], tau_delan[2]] # 3: DeLaN torques All 12 features are normalized using per-feature min/max scaling: feature_norm = (feature - feature_min) / (feature_max - feature_min)

5.5 Rolling History Buffer

The GRU processes a rolling window of 128 consecutive timesteps:

At timestep idx: buffer = deque(maxlen=128) # Circular buffer, auto-drops oldest Each step: feature_t = [q_t, qd_t, qdd_t, tau_delan_t] # (12,) buffer.append(feature_t) # Append normalized features Once buffer is full (idx >= 128): GRU input shape: (1, 128, 12) ↑ ↑ ↑ batch seq feature_dim GRU hidden state flows through 128 timesteps Output taken at final timestep (index 127): shape (3,)

5.6 GRU Warmup Phase (First 128 Steps)

Important: During the first 128 steps of trajectory execution (1.28 seconds at 100 Hz), the rolling buffer is not yet full, so GRU is not active. Only DeLaN is used during this warmup phase.

This is acceptable because:
1. Trajectory typically starts from a known, stationary pose where DeLaN accuracy is high
2. Most tracking error occurs later in the trajectory during dynamic motion
3. Once GRU activates after step 128, residual corrections improve overall accuracy

5.7 Why GRU for Temporal Modeling

A GRU (not just a feedforward MLP) is used because:

  • Temporal context: Robot dynamics have memory (past velocities, accelerations affect current torque needs)
  • Gate mechanism: GRU gates (reset, update) learn what historical information is relevant
  • Recurrent hidden state: Maintains information across timesteps, capturing temporal patterns
  • Efficiency: 4-layer GRU is more parameter-efficient than deep feedforward networks for sequence data

5.8 GRU Inference Pseudocode

def gru_predict(buffer, scaler, gru_model): """ Args: buffer: deque of (12,) feature vectors, length 128 scaler: StandardScaler fitted on training data gru_model: Trained PyTorch GRU model Returns: tau_residual: (3,) residual torque vector """ # Stack buffer into (1, 128, 12) tensor X = np.array(list(buffer))[np.newaxis, :, :] # (1, 128, 12) X_tensor = torch.FloatTensor(X).to(device) # Move to GPU if available # Forward pass (no gradient needed) with torch.no_grad(): y_pred = gru_model(X_tensor) # (1, 3) tau_residual = y_pred.cpu().numpy()[0] # (3,) return tau_residual

5.9 Strengths & Limitations

Strengths Limitations
Learns unmodeled effects (friction, backlash) Requires 128-step warmup (1.28 s delay)
Captures temporal patterns & memory Dependency on training data distribution
Improves DeLaN accuracy by ~10-30% Cannot extrapolate far outside training domain

6. Feedback Control & Error Correction

6.1 Error Signals (Closed-Loop)

At every 100 Hz control step, the controller compares desired trajectory to actual sensed state:

Position Error: e_pos[i] = q_des[i] - q_actual[i] [radians]
Velocity Error: e_vel[i] = q̇_des[i] - q̇_actual[i] [rad/s]

where q_actual and q̇_actual are obtained from the JointState ROS2 topic and filtered for noise.

6.2 Velocity Filtering

Raw joint velocities from Gazebo can be noisy. A first-order low-pass filter smooths them:

α = 0.25 # Low-pass filter coefficient (tunable) q̇_actual_filtered(t) = (1 - α) * q̇_actual_filtered(t-1) + α * q̇_actual_raw(t) This is a simple exponential moving average filter: - α = 0.0 → no update (pure delay) - α = 0.5 → 50% new data, 50% history - α = 1.0 → instantaneous (no filtering)

7. PID Control Law

7.1 Standard PID Formulation

The feedback torque is computed using a three-term PID controller with per-joint gains:

τ_fb[i] = K_p[i] · e_pos[i] + K_d[i] · e_vel[i] + K_i[i] · ∫e_pos[i] dt

or in vector form (element-wise):
τ_fb = K_p ⊙ e_pos + K_d ⊙ e_vel + K_i ⊙ ∫e_pos

7.2 Gain Values (Tuned)

Gain Joint 1 Joint 2 Joint 3 Unit Comment
K_p 20 80 20 Nm/rad J2 has strongest proportional control (heaviest)
K_d 3.5 18 10 Nm·s/rad Damping term prevents overshoot
K_i 0.2 0.8 0.1 Nm·s/rad² Small integral gain; limited to prevent windup

7.3 Why Different Gains for Each Joint?

  • Joint 1: Rotates base (horizontal plane). Lowest inertia. Moderate control effort needed.
  • Joint 2: Shoulder joint. Heaviest link (arm). Largest inertia. Needs strongest control (Kp=80, Kd=18).
  • Joint 3: Wrist joint. Lowest mass. Prone to oscillation. Moderate control with damping (Kd=10).

7.4 Proportional Term (K_p)

Provides immediate response to position error:

τ_p = K_p · e_pos = [20, 80, 20] · [error_j1, error_j2, error_j3] Effect: - Large error → large proportional torque - Small error → small proportional torque - Drives system toward desired position Problem if K_p is too high: - Overshoot (oscillation around setpoint) - Chattering (high-frequency oscillation)

7.5 Derivative Term (K_d)

Provides damping by penalizing velocity error:

τ_d = K_d · e_vel = K_d · d(e_pos)/dt Effect: - Resists rapid changes in error - Reduces overshoot from proportional term - Acts like viscous friction (proportional to velocity) Example: If K_p causes oscillation, increase K_d to dampen it.

7.6 Integral Term (K_i) & Anti-Windup

Removes steady-state bias by integrating position error over time:

τ_i = K_i · ∫e_pos dt Discrete integration (at each 10 ms step): integral_error[t] = integral_error[t-1] + e_pos[t] * dt τ_i = K_i · integral_error Problem (Windup): If error persists, integral term grows unbounded → actuator saturation → oscillation Solution (Anti-Windup): Clamp the integral error to a maximum value: integral_error = clip(integral_error, min=[-0.6, -1.2, -0.8], max=[0.6, 1.2, 0.8]) This prevents unbounded accumulation even if tracking error is large.

8. Feedback Enhancements & Safety Mechanisms

8.1 Gravity Compensation (Adaptive)

Even with PID feedback, large tracking errors can cause the arm to sag against gravity. An adaptive gravity compensation term is blended in as error grows:

τ_gravity = [0, -44*cos(q2), -12*cos(q2+q3)] # Joint 1: no gravity (horizontal rotation) # Joint 2: major gravity effect (lifting link) # Joint 3: minor gravity effect (wrist) Blending factor (grows with error): max_error_degrees = max(|e_pos|) * 180/π grav_blend = clip((max_error_degrees - 5°) / 25°, min=0.0, max=0.4) Interpretation: - If error < 5°: no gravity compensation (grav_blend = 0) - If error = 30°: full 40% gravity compensation (grav_blend = 0.4) - Ramps smoothly in between Applied to feedback: τ_fb_with_grav = τ_fb + grav_blend * τ_gravity

8.2 Feedback Low-Pass Filtering (Smoothing)

To reduce torque chatter and high-frequency oscillation on J3, the computed feedback torque is smoothed using a first-order filter:

α_fb = 0.35 # Low-pass filter coefficient τ_fb_smoothed(t) = (1 - α_fb) * τ_fb_smoothed(t-1) + α_fb * τ_fb_raw(t) = 0.65 * τ_fb_smoothed(t-1) + 0.35 * τ_fb_raw(t) Effect: - 65% from previous command (history/inertia) - 35% from current error (responsiveness) - Reduces rapid sign changes in feedback torque - Prevents aggressive joint reversals

8.3 Torque Slew Rate Limiting

To prevent rapid torque sign reversals (which cause oscillation), the rate of change of torque is limited to a maximum value per joint:

Slew rate limits (Nm/s): J1: 250 Nm/s J2: 300 Nm/s J3: 220 Nm/s ← Lower to prevent oscillation At each control step (dt = 0.01 s): max_delta = slew_limit * dt Example for J3: max_delta = 220 * 0.01 = 2.2 Nm per 10 ms step If commanded τ_new differs from τ_prev by > 2.2 Nm: τ_actual = τ_prev + clip(τ_new - τ_prev, -2.2, +2.2) Else: τ_actual = τ_new (no change needed) Effect: - Prevents aggressive sign reversals - Smooths torque profile - Reduces oscillation on low-inertia joints

8.4 Torque Saturation

Final safety check: hard limits on maximum torque per joint:

Torque limits: J1, J2: ±100 Nm J3: ±60 Nm (lower because it's lighter) τ_total = clip(τ_total, min=[-100, -100, -60], max=[100, 100, 60]) This ensures: - Actuators never exceed rated torque - Prevents damage to motors - Maintains safe operation

8.5 Summary of Feedback Enhancements

Enhancement When Applied Why Effect
Gravity compensation After raw PID Large errors → sagging → add gravity help Improves recovery from large errors
LPF feedback (α=0.35) After gravity blend Reduce torque chatter Smoother commands, less oscillation
Slew rate limiting After combining τ_dnn + τ_fb Prevent sign reversals Eliminates rapid flipping on J3
Torque saturation Final step before publish Enforce hardware limits Safe operation, no damage

9. Combined Control Law (Feedforward + Feedback)

9.1 Complete Torque Formula

τ_total = τ_dnn + τ_fb

= (τ_delan + τ_residual) + (K_p·e_pos + K_d·e_vel + K_i·∫e_pos + τ_gravity + τ_LPF)

where all terms are (3,) vectors (one per joint)

9.2 Step-by-Step Computation

┌─────────────────────────────────────────────────────┐ │ INPUTS (at timestep idx) │ ├─────────────────────────────────────────────────────┤ │ Desired State (from CSV): │ │ q_des = [dp1[idx], dp2[idx], dp3[idx]] │ │ qd_des = [dv1[idx], dv2[idx], dv3[idx]] │ │ qdd_des = [da1[idx], da2[idx], da3[idx]] │ │ │ │ Sensed State (from JointState topic): │ │ q_actual = [position_j1, position_j2, pos_j3] │ │ qd_actual = [vel_j1, vel_j2, vel_j3] (filtered) │ │ tau_sensed = [effort_j1, effort_j2, effort_j3] │ └─────────────────────────────────────────────────────┘ Step 1: DELAN INFERENCE (JAX) τ_delan = f_DeLaN(q_des, qd_des, qdd_des) Latency: 1-2 ms steady state Always active from step 1 Step 2: GRU RESIDUAL INFERENCE (PyTorch) if idx < 128: τ_residual = 0 # Warmup, buffer not full gru_active = False else: Append norm([q_des, qd_des, qdd_des, τ_delan]) to rolling buffer τ_residual = f_GRU(buffer[-128:]) Latency: 2-3 ms gru_active = True Step 3: COMBINE DNN OUTPUTS τ_dnn = τ_delan + τ_residual Step 4: COMPUTE ERRORS e_pos = q_des - q_actual e_vel = qd_des - qd_actual Step 5: UPDATE INTEGRAL WITH ANTI-WINDUP integral_error += e_pos * dt # dt = 0.01 s integral_error = clip(integral_error, min=[-0.6, -1.2, -0.8], max=[0.6, 1.2, 0.8]) Step 6: COMPUTE RAW PID τ_pid = K_p ⊙ e_pos + K_d ⊙ e_vel + K_i ⊙ integral_error = [20, 80, 20] ⊙ e_pos + [3.5, 18, 10] ⊙ e_vel + [0.2, 0.8, 0.1] ⊙ integral Step 7: ADD GRAVITY COMPENSATION q2 = q_actual[1]; q3 = q_actual[2] τ_gravity = [0, -44*cos(q2), -12*cos(q2+q3)] max_err_deg = max(|e_pos|) * 180/π grav_blend = clip((max_err_deg - 5) / 25, 0, 0.4) τ_pid_with_grav = τ_pid + grav_blend * τ_gravity Step 8: APPLY LOW-PASS FILTER TO FEEDBACK α = 0.35 τ_fb = (1 - α) * τ_fb_prev + α * τ_pid_with_grav τ_fb_prev = τ_fb # Save for next iteration Step 9: COMBINE FEEDFORWARD + FEEDBACK τ_combined = τ_dnn + τ_fb Step 10: APPLY SLEW RATE LIMITING max_step = [250, 300, 220] * dt # [2.5, 3.0, 2.2] Nm delta = clip(τ_combined - τ_prev_cmd, -max_step, +max_step) τ_limited = τ_prev_cmd + delta τ_prev_cmd = τ_limited Step 11: APPLY TORQUE SATURATION τ_total = clip(τ_limited, min=[-100, -100, -60], max=[100, 100, 60]) Step 12: PUBLISH COMMANDS /joint_1_controller/commands → τ_total[0] /joint_2_controller/commands → τ_total[1] /joint_3_controller/commands → τ_total[2] Latency: 0.3 ms (ROS2 transport) Step 13: LOG DATA (if enabled) Write timestep to CSV log: t, q_des, qd_des, qdd_des, q_act, qd_act, τ_delan, τ_dnn, τ_fb, τ_total, τ_sensed, e_pos, e_vel, gru_active, infer_ms, timings, ... └─────────────────────────────────────────────────────┘ Total latency per cycle: 3-15 ms (mostly DeLaN JIT + GRU)

9.3 Design Philosophy: Separation of Concerns

Key Design Principle:
  • Feedforward (DNN): Predicts torques for the PLANNED trajectory (q_des, qd_des)
  • Feedback (PID): Corrects errors using SENSED state mismatch (e_pos, e_vel)
This separation maintains interpretability and independent tunability. The DNN learns the nominal model, while PID adapts to reality.

10. Online Execution at 100 Hz

10.1 Control Loop Frequency

Target: 100 Hz (10 ms per control cycle) Actual: 10-15 ms typical (some deadline misses due to JAX warmup) dt = 0.01 s (timestep duration) T = 1/100 (period) f = 100 Hz (frequency)

10.2 Real-Time Constraints

At 100 Hz, the controller has 10 ms per cycle to:

Task Typical Duration Budget Remaining
Get joint state + filtering 0.5-1.0 ms 9.0-9.5 ms
Compute errors (e_pos, e_vel) 0.1 ms 8.9-9.4 ms
DeLaN inference (JAX) 1-2 ms (steady), 10-40 ms (warm-up) 6.9-8.4 ms or MISS
GRU inference (if active) 2-3 ms 3.9-6.4 ms
PID computation + limits 0.3 ms 3.6-6.1 ms
ROS2 publish + callback overhead 0.5 ms 3.1-5.6 ms ✓

10.3 JAX Warm-Up & JIT Compilation

JAX uses just-in-time (JIT) compilation to convert Python code to optimized GPU/CPU code. The first call to a JIT-compiled function is slow:

Timeline: Step 0: τ_delan() called for 1st time → JAX JIT compile in progress → ~20-40 ms delay → Control cycle MISSES 10 ms deadline Step 1-5: τ_delan() uses compiled code → ~1-2 ms latency → All steps MEET deadline Result: Occasional deadline misses only at startup Steady-state performance is within budget PID feedback tolerates brief delays

10.4 Inference Decimation (Optional)

To further reduce load, DNN inference can be decimated (run every Nth step):

infer_stride = 2 # Run inference every 2 steps if (idx % infer_stride) == 0: # Full DNN inference τ_dnn = dnn.predict(q_des, qd_des, qdd_des) last_tau_dnn = τ_dnn.copy() else: # Reuse previous output τ_dnn = last_tau_dnn inference_skipped = True Effect: - Every-other-step inference (20 ms apart) - Average latency reduced by 50% - One-step delay compensated by PID feedback - Small impact on tracking quality

This data is written to a rolling log file and can be analyzed post-execution to diagnose performance issues.

11.4 Timing Measurements

The controller tracks and logs several timing metrics to diagnose performance:

  • infer_ms: Latency of DNN inference (DeLaN + GRU)
  • control_dt_ms: Time elapsed since previous control callback (should be ~10 ms)
  • cycle_ms: Total duration of current callback (desired: <10 ms)
  • joint_state_age_ms: Age of most recent joint state message (-1 if not received)
  • deadline_miss_count: Number of cycles exceeding 10 ms + warning threshold
  • inference_skipped: Flag indicating inference decimation was used

Analysis of these metrics reveals bottlenecks and guides optimization efforts.

12. Gain Tuning & Performance

12.1 Tuning Methodology

Gains were tuned iteratively using data-driven analysis of tracking logs:

  1. Collect baseline data: Run trajectory with initial gains, log all states & errors
  2. Analyze performance: Compute RMSE, max error, p95 percentile for each joint
  3. Identify bottleneck: Which joint has worst tracking? (Typical: J2, then J3)
  4. Diagnose root cause:
    • Large position error → increase Kp
    • Overshoot/oscillation → increase Kd
    • Slow convergence → increase Ki (slightly)
  5. Iterate: Adjust single joint gains, re-run, measure improvement
  6. Validate: Check that improvements don't destabilize other joints

13. Challenges & Solutions

13.1 Challenge: DNN Inference Latency

Problem: JAX DeLaN first-call warm-up can take 10-40 ms, exceeding the 10 ms control cycle budget. Result: deadline misses on first few steps.

Solution Implemented:

  • JAX JIT compilation happens once at startup inside the DNNInferenceEngine constructor
  • Dummy forward pass warm-ups the JIT before trajectory starts
  • After warm-up, steady-state latency is 1-2 ms
  • Controller tolerates brief deadline misses due to PID feedback adaptability

13.2 Challenge: GRU Warmup Delay

Problem: GRU requires 128-step history (~1.28 s at 100 Hz) before it can predict residuals. During warmup, only DeLaN is used, which may have model errors.

Solution Implemented:

  • During GRU warmup, DeLaN-only prediction is acceptable because:
    • Trajectory typically starts from a known, stationary pose where DeLaN is most accurate
    • Most tracking errors occur later during high-speed dynamic motion
    • Once GRU activates after step 128, residual corrections improve accuracy for the bulk of the trajectory
  • Log includes gru_active flag so users can see when GRU became active

13.3 Challenge: J3 Torque Sign-Flip Oscillation

Problem: J3 exhibited rapid torque reversals (sign changes), causing position oscillation. Root cause: low inertia + Coriolis coupling with J2 → unstable feedback.

Solutions Implemented:

  • Increase derivative gain: K_d from 8 → 10 Nm·s/rad (more damping)
  • Reduce proportional gain: K_p from 24 → 20 Nm/rad (less aggressive)
  • Add torque slew rate limiting: Max 220 Nm/s on J3 (prevents rapid sign-flip)
  • Add feedback LPF: α = 0.35 smooths torque commands
  • Increase infer-stride: Run DNN every 2 steps, reuse in between (reduces command changes)

Result: Oscillation greatly reduced; J3 errors now stable at 7-8° RMS

13.4 Challenge: Control Loop Deadline Misses

Problem: 100 Hz control loop missed 10 ms deadline ~50-90% of the time, causing phase lag and degraded tracking.

Solutions Implemented:

  • Inference decimation: Run DNN every 2 steps (infer_stride=2), reuse in between → 50% latency reduction
  • Marker publishing decimation: Publish visualization markers every 20 steps instead of every step
  • Feedback LPF: Reduces command chatter, smooths execution
  • Console logging decimation: Print summary every 50 steps instead of every step

Result: Average cycle_ms improved; deadline miss rate decreased

13.5 Challenge: Command vs. Sensed Torque Mismatch

Problem: Commanded vs. sensed torques differed significantly, especially J2 (mean 8 Nm, p95 22 Nm), suggesting actuator saturation or lag.

Explanation & Solution:

  • This mismatch is expected in simulation due to:
    • Gazebo joint motors have finite bandwidth
    • Motor dynamics not fully modeled in inverse dynamics
    • Joint friction/backlash not perfectly captured
  • The PID feedback adapts by comparing desired vs. actual joint motion, not torques, so it compensates automatically
  • Sensed torque mismatch doesn't degrade performance significantly

13.6 Challenge: Trailing Motion After Trajectory End

Problem: After the last trajectory step, the arm continued moving slightly due to inertia, drawing a small extra path segment in RViz visualization.

Solution Implemented:

  • Publish zero torques immediately at trajectory completion
  • Stop appending new points to live path marker after trajectory ends
  • This prevents visualization from showing the settling tail

13.7 Challenge: Model Error at Large Tracking Errors

Problem: When tracking error exceeds ~5°, DeLaN's evaluation at desired pose (q_des) becomes inaccurate because the actual arm configuration is different.

Solutions Available:

  • Adaptive gravity blending (implemented): As error grows, gradually introduce gravity compensation to help arm recover
  • Use actual frame (optional): Evaluate D(q_actual) instead of D(q_des) to adapt to real pose (available via --model-frame actual, not recommended)
  • Increase feedback gains: Stronger PID can overcome model errors (already tuned)

13.8 Challenge: Training Data Distribution Mismatch

Problem: If online test trajectory is very different from training trajectories, GRU predictions may be outside its training domain and less accurate.

Mitigation Strategies:

  • Diverse training data: Train on many different trajectories (straight lines, spirals, random)
  • Extrapolation robustness: Use regularization (dropout, L2) to prevent overfitting
  • Fallback to DeLaN: If GRU residuals are suspicious, physics baseline is always available
  • Ensemble methods: Multiple GRU models with voting (advanced, not implemented)

Summary: How the DNN Controller Works

The DNN-based trajectory controller for the PUMA-560 arm exemplifies modern hybrid control architecture:

Feedforward (DNN)

  • DeLaN: Learns physics (D, C, G)
  • GRU: Learns residual errors
  • Result: Data-driven torque prediction

Feedback (PID)

  • Error sensing: e_pos, e_vel
  • Proportional: Immediate response
  • Derivative: Damping & stability
  • Integral: Steady-state correction

Key Features:

  • Real-time execution: 100 Hz (10 ms) control loops with sub-3 ms inference latency
  • Hybrid architecture: Combines learning (DNN) with classical control (PID)
  • Safety mechanisms: Anti-windup, slew limiting, torque saturation, gravity blending
  • Adaptability: Feedback compensates for model errors and disturbances
  • Interpretability: Separation of feedforward and feedback allows diagnosis & tuning
  • Generalization: Physics-based DeLaN plus learning-based GRU residual

Performance:

  • J1: 0.3° RMS error (excellent)
  • J2: 2.3-3.2° RMS error (good, heaviest joint)
  • J3: 6.9-7.9° RMS error (fair, oscillation-prone due to low inertia)

This architecture demonstrates how combining data-driven learning with classical control can achieve robust, accurate trajectory tracking for complex robotic systems.
